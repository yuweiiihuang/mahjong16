# 牌局紀錄與研究資料：第一版規劃

狀態：引擎紀錄、JSON 重播、SQLite 網頁保存、接管/來源紀錄、結算與 Docker
持久化設定已實作；研究觀察匯出、戰績身份與 CI/CD 仍為規劃。
先在 Mac 驗證，不改動 Windows 正式服務。

## 目標與範圍

同一份可驗證的牌局紀錄，支援朋友對局的戰績及研究資料匯出。
第一版做到保存、重播、匯出；不包含重啟續局、帳號系統、排行榜或訓練演算法。
紀錄有無啟用不應改變規則、吃碰胡裁決、玩家可見資訊或機器人選擇。

## 現有程式的接點

- `domain/gameplay/game_env.py`：共同的 reset/step 邊界；網頁及 self-play 都用這個引擎。
- `domain/table/deal.py`：建立牌牆、座位、發牌與初始補花。
- `app/web.py`：WebTable.apply 執行動作；settle 計算結算。
- `app/web_rooms.py`：座位接管、真人/機器人切換、請求重試及開始牌局。
- `app/runtime.py`、`app/session/ports.py`：CLI 已有開始、步驟及結算通知。
- `app/logging.py`：已有結算 CSV，可沿用其欄位概念，不當作完整牌譜。
- `rl/selfplay.py`：已有記憶體中的樣本收集，第一版不重寫訓練流程。

WebTable.events 只留最近 60 筆，且刻意省略未採用的反應；playback 是畫面播放用。
兩者都維持原用途，不能當作研究紀錄或把伺服器私有紀錄送進 snapshot。

## 紀錄格式

採用版本化 JSON payload 搭配少量 SQLite 索引欄位。
資料格式版本、引擎 commit/建置版本與規則/計分設定都需記錄。
不能只保存 seed：連續牌局共享亂數進度，程式版本也可能改變抽牌順序。

每局保存：

1. 局 ID、桌 ID、局次、時間、來源（web/CLI/self-play）、開始與結束狀態。
2. 初始牌牆順序與座位/莊家/圈風設定；可序列化的初始引擎狀態及補花結果。
   先明確列出重播必要欄位，不直接 pickle 整個引擎。
3. 依伺服器接受順序編號的動作：座位、階段、反應窗口 ID、動作內容、
   來源（真人、bot、自動過、自動聽牌出牌）、步驟結果及狀態校驗值。
4. 真人決策時實際可知的觀察與合法操作；不包含別家的暗牌、牌牆、
   其他玩家未公開的反應資格。現有 `_obs` 不直接當作此契約，先檢查可見性。
5. 吃碰胡提交與裁決分開：被蓋過的選擇仍保留；提前裁決而未收到回覆的座位，
   記為未回覆，不推定為 PASS。決策上下文取自該窗口開始時，不混入後到的私有回覆。
6. 座位接管事件：玩家代號、名稱快照、真人/bot 切換及有效步驟範圍。
7. 完成時的胡牌/流局、台數明細、每座位收付分及桌內累計分。

拒絕的非法或過期請求不當作遊戲步驟；成功請求重試不重複記錄。
摸牌與補花可能在一步內發生，保存能重建的結果，而不是只保存畫面上按的按鈕。
開局發牌即花胡也需有開始及完成紀錄。

## 保存方式

先使用 Python 標準庫 sqlite3，不增加獨立資料庫服務或 ORM。
第一版實作以單一 hands 表保存完整 JSON，沿用既有牌譜驗證格式；
步驟與接管資訊保存在 payload 中。原規劃的 steps/seat_events 分表留待實測資料量與
寫入延遲有需要時再做，避免先增加兩套序列化方式。

檔案路徑由啟動參數指定；正式版放 Docker 持久化資料空間，Mac/CI 分開使用測試資料。
資料不放進 Git、映像或網站靜態目錄；不保存通行碼、cookie、SSH 金鑰或原始登入 token。
第一版身份只代表已建立的玩家代號/連線來源，不以同名認定同一人，亦不宣稱跨裝置身份。
穩定跨次戰績身份是後續功能；混合真人/bot 接管的局先標記，不盲目計入個人勝率。

每個接受的步驟及完成結算以短交易提交，不只等整局結束才保存。
共用 recorder 保持可選，引擎只交付紀錄資料，不自行開啟資料庫。
Web 多執行緒的寫入需序列化，維持引擎及資料庫鎖的一致順序；不用背景佇列先換取速度。

記憶體變更與 SQLite 不可能自然成為同一交易：保存失敗時停止該桌後續動作，
明確回報並保留最後已提交步驟，不能仍回覆成功、默默漏記或重新套用動作。
先驗證逐步寫入耗時，避免重新引入出牌停頓。

## 重播及研究匯出

第一版提供離線 CLI，使用同一引擎逐步套用紀錄，檢查中間狀態和結算。
重播需相符的引擎與格式版本；不假設新版引擎永遠能重播舊紀錄。
研究匯出使用 JSONL，一筆一個決策，保留局/步驟/座位/控制來源/版本。

環境一步不等於同一玩家下一個決策：不能直接拿 env.step 回傳的下一位觀察
當作當前玩家的 next_obs。第一版先匯出決策事實與最終收付分；
reward 定義、同玩家轉移及未完成局篩選在研究用途明確後再轉換。
不要把真人選擇標成最優操作，不把未回覆標成拒絕，不把收付分等同引擎即時 reward。

私有牌譜只供管理/研究匯出；日後玩家牌譜 API 另做可見性與存取檢查。

## 實作順序與驗收

1. 固定格式、共同 recorder 接點與初始狀態；固定測試牌局可逐步重播並得到相同結果。
2. 接 SQLite 與網路牌桌生命周期；涵蓋真人、bot、自動動作、反應裁決及接管。
3. 接結算與 CLI/研究匯出；沿用既有計分，記錄一次，不在儲存層重算另一套規則。
4. 接 Docker 持久化與資料庫備份/還原；本機容器更新後紀錄仍在，正式切換另行批准。
5. 基礎驗收後才接 CI/CD、戰績畫面及穩定玩家身份。

必要驗收案例：

- 正常胡牌、流局、補花/槓、自動聽牌出牌、開局花胡。
- 多家同時回應、不同提交順序、吃被碰/胡蓋過、提前裁決未回覆。
- 中途加入、離開及 bot 接管；重試不產生重複步驟或結算。
- 啟用紀錄與停用紀錄，同一動作序列結果一致。
- 保存失敗不假裝成功；停止程序後可讀已提交前綴，未完成局不當作輸局。
- 紀錄不洩漏到玩家 snapshot；重播逐步狀態及最終收付分一致。
- 備份可還原至另一個測試檔，Docker 容器替換不清掉資料。

備份採資料庫支援的一致性方式，不能在寫入中只複製主檔而忽略日誌。
未完成局保存為未完成/中斷，不自動恢復成正在玩的房間。

## 第一版不做

PostgreSQL、Redis、Kubernetes、網頁重播播放器、登入帳號、排行榜、
重啟續局、大規模 RL 訓練自動保存及每一步四家完整 UI 快照。
先驗收保存與重播，之後依實際資料量/寫入耗時擴充。
